# tg-client-manager

`tg-client-manager` — это оркестратор, управляющий жизненным циклом персональных Telegram-клиентов (`tg-client`) внутри Kubernetes кластера.

## Принцип работы
Вместо того, чтобы держать все подключенные Telegram-аккаунты в одном Node.js процессе, система использует архитектуру **"per-user pod"**. `tg-client-manager` выполняет роль контроллера, который следит за Redis и динамически поднимает Kubernetes Pod для каждого авторизованного пользователя. Если пользователь закрыл доступ или мы не можем авторизоваться, помечаем его и больше не пытаемся залогиниться, пока пользователь не изменит что-то.

## Основные функции
1. **Синхронизация подов**:
   - Читает список активных сессий (auth state) из Redis (ключ: `tg_users` или ключи `tg_session_*`).
   - Сравнивает желаемое состояние со списком реально работающих подов в Kubernetes (label `app: tg-client-user`).
   - Автоматически создает Deployment/Pod для новых пользователей и удаляет для тех, кто вышел из аккаунта (logout).
2. **REST API**:
   - Предоставляет внутреннее API на порту `3000` для управления сессиями.
   - Endpoint: `/api/telegram/logout/:id` для завершения сессии и удаления связанного пода.
   - (Используется дашбордом `src/components/dashboard` для отображения и управления Telegram).

## Настройки (Environment Variables)
- `.env`: Все секреты и настройки.
- `REDIS_URL`: Подключение к Redis (источник правды о сессиях).
- `NAMESPACE`: Kubernetes namespace, в котором создаются поды (по умолчанию `debugging-testcrash-pub` ).
- `TG_CLIENT_IMAGE`: Docker-образ, используемый для создания подов (например: tg-client:latest`).
- `WHISPER_SECRET` / `WHISPER_PROVIDER`: Пробрасываются внутрь создаваемых клиентских подов.

## Как разворачивается
Разворачивается один экземпляр (Deployment) в кластере (`kubernetes/base/tg-client-manager.yaml`). Ему необходимы права на управление Deployment/Pods в Kubernetes (`Role` и `RoleBinding` с ресурсами `deployments`, `pods`).

## Почему такая архитектура?
1. **Изоляция**: Падение одного клиента (например, из-за ошибки в `tdlib` или out-of-memory) не затрагивает остальных пользователей.
2. **Масштабируемость**: Kubernetes берет на себя рестарт упавших контейнеров и балансировку ресурсов.
3. **Безопасность**: У каждого пода только своя сессия `tdlib` в отдельной эфемерной ФС.
